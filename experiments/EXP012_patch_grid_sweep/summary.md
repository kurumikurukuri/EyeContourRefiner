## 前提：各パラメータの意味（コード実装ベース）

`utils/patch_utils.py::extract_patch` の affine 変換より：

```
scale       = (patch_w - 1) / ((t_max - t_min) * |PQ|)   # 画像→パッチ（t軸方向）
actual_perp = (patch_h - 1) / (perp_scale * |PQ|)         # 画像→パッチ（法線方向）
```

| 軸 | 画像上の **カバー範囲** を決める | 出力パッチの **サンプリング解像度** を決める |
|----|-------------------------------|-----------------------------------------|
| t軸（PQ方向） | `t_min` / `t_max` | `patch_w` |
| 法線方向（PQに垂直） | `patch_perp_scale` | `patch_h` |

つまり `patch_w` / `patch_h` を大きくしても **画像上でサンプリングする領域は変わらず、単に出力パッチの解像度が上がる**（上流の画像信号は同じ、下流の CNN が処理するテンソルが大きくなるだけ）。

## 考察

### 1. patch_w の影響：解像度は 64 で十分、高解像度化は悪化

`patch_w=64` が一貫して最良。`w=256` は平均で `+0.0036` 悪化（全体レンジの約37%）。

重要：これは **「パッチが取り込む画像領域が広がってノイズが入った」わけではない**（t_min/t_max が同じなら画像上のカバー範囲は不変）。原因は以下のいずれか/複合と考えられる：

- **オーバーサンプリング**：w=64 で既に情報は飽和しており、w=128/256 は補間による冗長画素を増やすだけで新規情報は増えない
- **CNN の受容野**：`num_conv_layers=3` で w=256 だと最終特徴マップ上の 1 画素が覆う入力領域（受容野）がパッチ全体に届かず、t軸方向のグローバル文脈を捉えづらい
- **計算コスト・学習難度の増加**：パラメータ数・FLOPs が増え、同一エポック数での最適化が困難になる・過学習しやすくなる

→ 「w=64 で十分」は正しいが、理由は「t 範囲が既に捉えられている」ではなく「このアーキテクチャ構成下ではサンプリング解像度 64 で情報が飽和する」と解釈すべき。

### 2. perp_scale=1.0 がロバストに最良（唯一の「画像範囲」因子）

perp_scale は **法線方向の画像上のカバー範囲**を直接制御する因子。1.0 が全 patch_w で最良で交互作用も小さい。
- 0.5（範囲 = |PQ|×0.5、狭い）：アイライナーの上下端を取りこぼす可能性
- 2.0（範囲 = |PQ|×2.0、広い）：上まぶた・眉・肌など余分な情報が入りノイズ化
- 1.0（範囲 = |PQ|×1.0）：必要十分

これは **唯一、画像信号の質的変化を起こす因子**であり、最適値が明確なのは意味的にも妥当。

### 3. patch_h の影響は軽微（解像度因子のため当然）

h=32/64/128 の差は平均 `0.0006` 未満と僅差。法線方向のカバー範囲は `perp_scale` が決めるため、`patch_h` はそのサンプリング解像度を変えるだけ。範囲が固定なら解像度 32 で十分という結果は `patch_w` と同趣旨。

※ ただし `patch_h < patch_w` のアスペクト比（例: 32×64, 64×128）の方が上位に多く、**縦圧縮気味のサンプリングが学習に有利**な可能性はある（要検証）。

### 4. t_min / t_max の影響（これが画像範囲の横方向因子）

- **C（t_min=-1.25, t_max=2.0）が唯一の明確な劣位**：平均 0.059524（他3グループは 0.058699〜0.058832）
- t_min を -1.0→-1.25 に広げること単独では有害（Cの劣化）
- ただし t_max も同時に 2.25 に広げる（D）と劣化が抑えられ A/B と同水準
- → **t_min を広げるなら t_max も同時に広げるべき**（patch 範囲の非対称性が問題）
- A（ベースライン）と B の差は僅少（平均差 < 0.0002）で、t_max の +0.25 拡張はほぼ中立

補足：`patch_w` を固定して `t_min/t_max` のみ広げると、**画像上の同じ|PQ|を w=64 ピクセルに詰め込む密度**が下がる（= 空間解像度が実質的に下がる）。C の劣位は「範囲の非対称化」に加え、「t軸の実効解像度低下」も寄与する可能性がある。

### 5. ベスト構成の推奨

| パラメータ | 推奨値 | 根拠 |
|-----------|-------|------|
| patch_w | 64 | サンプリング解像度として十分。それ以上は情報増なし＋学習難度増 |
| patch_h | 64 | h=32 とほぼ同等だが、法線方向の情報取りこぼしリスクを避けマージンを確保 |
| perp_scale | 1.0 | 法線方向カバー範囲として最適（画像範囲因子） |
| t_min | -1.0 | A/B グループの方が C より優位（範囲の対称性） |
| t_max | 2.0 or 2.25 | 差が軽微なのでどちらでも可（A ≈ B） |

**推奨ベスト条件：`A_p10_h064_w064`（holdout_mae=0.056123）**
（または同等の B_p10_h064_w064=0.056137、差異は誤差範囲内）

### 6. 今後の方針

- `patch_w=64` / `patch_h=64` / `perp_scale=1.0` / `t_min=-1.0` / `t_max=2.0` に固定して次実験へ
- **解像度 × アーキテクチャの交互作用**：`num_conv_layers` を増やして受容野を広げた場合、patch_w=128/256 が活きる可能性あり（今回の w 劣位は固定アーキ下の結果）
- **画像範囲（perp_scale, t_min/t_max）の微調整余地**：0.5〜2.0 の粗い格子だったので、0.8/1.0/1.2 程度の細かい探索があり得る
- EXP013 以降では入力解像度より **augmentation / loss / backbone** の寄与を優先的に検証
