# EXP037: ルールベース補正（face_makeup）と ML 補正（eye_contour_refiner.onnx）の比較

## 目的

[face_makeup#1](https://github.com/kurumikurukuri/face_makeup/issues/1) のモデル側受け入れ条件 2 つを検証する。

1. 同じ画像セットで、ルールベース補正と ML 補正の**補正点を比較する**
2. 同じ画像セットで、ルールベース補正と ML 補正の**処理時間を計測して記録する**

仮説:

1. ML 補正はルールベース補正より正解（アノテーション）に近い
2. 処理時間は ML の方が長いが、1 顔あたり数十 ms に収まる

## 実験設計・条件

### 共通

- **データ**: `manifests/manifest_test.csv` = db_replica 固定テストセット（EXP030 以降の標準。EXP035 から複製）。
  4,900 点 / 350 眼 / 299 顔 / 298 画像。目単位では全て 14 点（upper 7 + lower 7）揃っているが、
  顔単位では片目のみ 248 顔・両目 51 顔
- **ルールベース**: face_makeup commit `090342707bc5bcca3b8b5fadd39edc37081f3084` の `EyelinerCorrector`
  （`pyproject.toml` の exp037 extra で commit 固定）。`preprocess()` → `find_edge(return_debug_info=True)` を点ごとに呼ぶ。
  `correct_points` と同一の出力であることを `tests/test_exp037_refiners.py` で検証済み
- **ルールベースの入力座標**: face_makeup 本番（`renderer.py`）は `FaceLandmarks.to_image_coords` で
  座標を `np.round` → int32 にしてから `correct_points` に渡すため、ルールベースには**同じ丸めをした P,Q** を渡す
  （丸めが本番と一致することもテストで検証）。小数の P,Q をそのまま渡した場合は参考値（`rule_float`）として併記する
- **ML**: `models/eye_contour_refiner.onnx`（EyeContourRefiner main からコピー、git 管理外。
  sha256 `b380f7de629cefa13633ae95d527310868b28f2d5c3014bc109f15288441833d`）。入力は DB の小数の P,Q。目単位 14 点を 1 バッチで推論。
  中身は EXP035 J4_rot20（PQ 回転摂動 ±20°）で、EXP036 で標準に選んだ J3（±15°）とは別モデル
  （EXP036 では J3 と J4 の差 0.12%、全 seed n.s.）。本実験の結論は配布 ONNX についてのもの
- **実行環境**: Intel Core i7-12700（20 論理コア）/ Windows 11 / Python 3.11.9 / numpy 1.26.4 /
  OpenCV 4.11.0 / onnxruntime 1.31.0（CPUExecutionProvider）

### 1. 補正点の比較の条件

- **対象**: 全 4,900 点（298 画像）
- **t の比較方法**: ルールベースの出力点は、正解を定義している元の（小数の）P-Q 直線に射影し、
  モデルの規約 `R = t·P + (1-t)·Q` の t に変換する（face_makeup は `R = P + s·(Q-P)`, `s ∈ [0, 0.5)` を探索するので `t = 1 - s`）
- **評価指標**: MAE(t)、ピクセル誤差（正解点 R_true とのユークリッド距離）、pass_std / pass_strict
  （`experiments/Completion_Criteria.md` 準拠）、ルールベースの fallback 率
- **検定**: `scripts/paired_ttest.py`（点単位、raw_t と error_ratio の両方）に加え、同じ画像の点は独立でないため
  画像単位の平均誤差で Wilcoxon 符号順位検定 + 画像単位ブートストラップ（10,000 回）

### 2. 処理時間の計測条件

- **対象**: 両目 28 点が揃った 51 顔（51 画像、0.59〜1.05 MP、中央値 約 0.70 MP）のみ
- **計測区間**:

| | 区間に含める | 区間外 |
|---|---|---|
| 共通 | 入口 = 読み込み済み RGB 画像 + 28 点の P,Q / 出口 = 28 点の補正点 R | 画像読み込み・デコード、MediaPipe、座標の丸め |
| ルール（本番構成、主結果） | 目ごとに preprocess（画像全体の bilateralFilter → グレースケール → 正規化）+ find_edge × 14 を左右 2 回 | corrector 生成（毎回新規にして前処理キャッシュを無効化） |
| ルール（前処理共有、参考） | preprocess 1 回 + find_edge × 28 | 同上 |
| ML | eye_scale × 2 眼 + パッチ切り出し 56 枚 + テンソル化 + session.run（28 点 1 バッチ）+ R 変換 | InferenceSession 生成（別記録） |

- **本番との差（find_edge の回数）**: 本番の `correct_points` は `EYELINER_CORRECTION_MAP` のうち
  `EDGE_LANDMARK_DIRECTIONS` にある点を 1 目あたり 16 回補正する（アノテーション対象外の目尻 1408 / 1608 と、
  upper・lower の両方に含まれる 1507 / 1707 の重複を含む）。本実験はアノテーション済みの 14 点だけを補正するので、
  本番より 1 顔あたり find_edge が 4 回少ない。find_edge は約 0.1 ms/点（エッジ探索 2.8 ms / 28 点）なので
  差は約 0.4 ms（本番構成の合計の約 2%）で、ML / ルール（本番構成）の比は 1.47 → 約 1.45 倍と結論は変わらない

- **ルールの 2 条件**: face_makeup 本番は左右の `EyelinerPass` がそれぞれ `EyelinerMaskStrategy` → `EyelinerCorrector` を持ち
  （`face.py`・`passes/eyeliner.py`）、前処理キャッシュは corrector ごとなので、**1 顔で画像全体の前処理が 2 回走る**。
  これと同じ構成（`rule_per_eye`）を主結果とし、前処理を左右で共有した場合（`rule`）を参考値とする
- **繰り返し**: ウォームアップ 5 顔の後、「全 51 顔を 1 周」を 20 回繰り返して計測。
  3 方式の実行順は顔と周回ごとに巡回させ、各方式が各順位に均等に来るようにした。顔ごとの中央値を取り、それを 51 顔で集計
- **スレッド数**: 次の 2 条件
  - 既定（主結果）: スレッド数を指定しない。OpenCV は 20 スレッド（論理コア数）、onnxruntime は既定の設定
  - 単一（参考）: `cv2.setNumThreads(1)`、onnxruntime の `intra_op_num_threads` / `inter_op_num_threads` を 1
- **負荷条件**: 常駐アプリ（ブラウザ・チャット・ゲームランチャー等）を停止して計測。
  当初は顔ごとに 20 回連続で計測していたが、常駐アプリの一時的な負荷が連続する顔に集中して結果が実行ごとに
  大きく変わったため、上記の「1 周 × 20 回」に変更した
- **再現性**: 同条件で 2 回実行し、中央値の差は既定スレッドで 1.3 ms 以内、単一スレッドで 3.6 ms 以内だった
  （掲載値は 2 回目。詳細は「その他」）

## 1. 補正点の比較（受け入れ条件 1）

**要点: ML はすべての t 帯・上下瞼でルールベースより正解に近い。pass_std 42.7% → 90.0%、平均ピクセル誤差 2.55 → 0.77 px。**

#### ルールベースの失敗要因

ルールベースの誤差には、アルゴリズムの仕様に由来する 3 つの要因がある。

**注記 1: fallback（エッジ未検出）**

- face_makeup は P→Q 方向の輝度プロファイルで 2 次微分のゼロ交差を探し、1 次微分が閾値（`_GRAD_THRESHOLD = 0.1`）を
  超える交差のうち最大のものをエッジとする。条件を満たす交差が無いと（サンプル数不足などの場合も）、補正せずに P をそのまま返す
- 全体の 15.2%（744 点）が fallback になった。t_true < 0.3（正解が Q 寄り）の帯で約 50%（t<0: 54%、0-0.3: 47%）と多い
- fallback 点に限るとルールの pass_std は 9.3%、平均ピクセル誤差は 4.26 px。ML は同じ点で 91.8%・0.67 px で、
  ML は fallback 点を苦手としていない

**注記 2: 探索範囲外の正解**

- face_makeup は `R = P + s·(Q-P)`, `s ∈ [0, 0.5)` を探索する。t に直すと t ∈ (0.5, 1] で、
  正解がこの範囲の外（t ≤ 0.5 または t > 1）にある点は原理的に正しく補正できない
- 正解の 24.9%（1,221 点）が範囲外にある。範囲外の点に限るとルールの pass_std は 15.1%、ML は 81.8%

**注記 3: 出力の整数切り捨て**

- face_makeup は補正点の座標を `int()` で切り捨てる。P-Q 距離は中央値 9.3 px と短いため、1 px の切り捨てで t が約 0.1 ずれる
- 出力 t が探索範囲 (0.5, 1] の外の 0.34〜1.28 に広がるのはこのため
- 切り捨てを外すと（`rule_untrunc`）全体の pass_std は 42.7% → 50.4% に上がる

**要因の重なり**: fallback 744 点のうち 408 点は探索範囲外の点でもある（fallback のみ 336 点、範囲外のみ 813 点）。
fallback か範囲外の少なくとも一方に当たる点は全体の 31.8%（1,557 点）。

#### 失敗要因を除いた比較（参考）

ルールベースに有利になるよう失敗要因を除いて、ML と比べ直した。fallback と探索範囲外は該当点を除き、
整数切り捨ては切り捨て前の出力（`rule_untrunc`）で評価した（点は除かない）。ML の値は同じ点集合で集計しており、
整数切り捨ての有無には影響されない。

|---|---|---|---|---|---|---|---|
| ① 全点（主結果） | 4900 | 0.267 | 0.081 | 2.55 | 0.77 | 42.7 | 90.0 |
| ② fallback を除く | 4156 | 0.212 | 0.079 | 2.24 | 0.79 | 48.7 | 89.7 |
| ③ 探索範囲外を除く | 3679 | 0.175 | 0.066 | 1.97 | 0.68 | 51.8 | 92.7 |
| ④ 整数切り捨てなし | 4900 | 0.243 | 0.081 | 2.27 | 0.77 | 50.4 | 90.0 |
| ⑤ ② + ③ | 3343 | 0.156 | 0.065 | 1.88 | 0.69 | 55.6 | 92.6 |
| **⑥ ② + ③ + ④（3 要因すべて除く）** | 3343 | **0.128** | **0.065** | **1.52** | **0.69** | **66.3** | **92.6** |

- 3 要因をすべて除いても、ルールの pass_std は 66.3% で ML（92.6%）に 26 ポイント届かない。
  MAE は ML の約 2 倍、ピクセル誤差は約 2.2 倍
- 単独の要因で差が大きいのは探索範囲外（③で pass_std +9.1 ポイント）と整数切り捨て（④で +7.7 ポイント）。
  fallback の除外（②）は +6.0 ポイント
- ③・⑤・⑥は正解 t_true を使って点を選んでいるため、本番では再現できない。ルールベースの性能の上限に近い参考値として扱う

### 考察

- 仮説 1 は支持された。ML はすべての t 帯・上下瞼でルールベースより正解に近く、画像単位でも 298 画像中 297 画像で ML の方が良い。
  差が特に大きいのは t < 0.3 と t ≥ 1.2 の帯（ルール pass_std 0〜9%、ML 64〜72%）で、ルールの探索範囲外・fallback が集中する領域と一致する
- ルールベースの誤差の一部は、探索範囲（t > 0.5 かつ t ≤ 1）の制約、エッジ未検出時の fallback、出力の整数切り捨ての
  3 つから生じている。どれも閾値調整では解消しにくい構造的な制約で、issue の課題認識と一致する
- ただし 3 要因をすべて除いても ML との差（pass_std 66.3% 対 92.6%）は大きく残る。
  ルールの弱点は仕様上の制約だけではなく、エッジ（勾配）検出で決めた位置そのものが正解からずれていることにもある。
  このため、探索範囲の拡張や切り捨ての廃止といったルール側の改修だけでは、ML の精度には届かないと考えられる
- **face_makeup 側への参考**: ML に本番と同じ整数座標（eye_scale も整数座標から計算）を入れた場合も
  pass_std は 89.49%（小数座標 90.02%）、MAE は 0.0823（同 0.0811）で、座標の丸めによる精度低下は小さい
  （`points_exp037.csv` の `*_ml_int` 列、`analysis_exp037.json` の `ml_int`）

## 2. 処理時間の計測（受け入れ条件 2）

**要点: 1 顔（28 点）あたり中央値で ML 34.7 ms / ルール（本番構成）23.6 ms（既定スレッド）。ML はルールの約 1.5 倍。**

### 結果

以下の値はすべて **1 顔（両目 28 点）を補正するのにかかった時間（ms）** である。
各顔で 20 回計測した中央値をその顔の値とし、51 顔分を集計した（例: 「中央値」は 51 顔の値の中央値）。

| 統計量（51 顔） | ルール（本番構成） | ルール（前処理共有、参考） | ML | ML / ルール（本番構成） | ML / ルール（前処理共有） |
|---|---|---|---|---|---|
| **中央値** | **23.6** | 13.0 | **34.7** | **1.5 倍** | 2.7 倍 |
| 平均 | 24.6 | 13.5 | 34.7 | 1.4 倍 | 2.6 倍 |
| p95（95% の顔がこの時間以内） | 29.3 | 15.7 | 35.4 | 1.2 倍 | 2.3 倍 |
| 最小〜最大 | 22.4〜32.1 | 12.3〜16.9 | 33.6〜35.8 | – | – |

#### 工程別の内訳（既定スレッド、中央値）

| 方式 | 工程 | 時間 (ms) | 処理内容 |
|---|---|---|---|
| ルール（本番構成） | 前処理 × 2 | 20.4 | 画像全体の bilateralFilter → グレースケール → 正規化（`preprocess`）を左右の目で 1 回ずつ |
| ルール（本番構成） | エッジ探索 | 2.8 | 28 点それぞれで P→Q 方向にエッジを探す（`find_edge` × 28） |
| ルール（前処理共有） | 前処理 | 10.1 | `preprocess` 1 回 |
| ルール（前処理共有） | エッジ探索 | 2.6 | `find_edge` × 28 |
| ML | パッチ作成 | 4.2 | 56 枚のパッチ切り出し + 入力テンソル作成 |
| ML | 推論 | 30.3 | `session.run`（28 点を 1 バッチ） |

- 各工程の中央値は工程ごとに独立に取っているため、足しても合計の中央値と一致しない
- ML の合計には、内訳に含まれない eye_scale の計算（2 眼）と出力 t → 補正点 R の変換も含まれる
- ルールは前処理、ML は推論が時間の大半を占める。本番構成のルールは同じ画像の前処理を 2 回行うため、共有版の約 1.8 倍かかる

#### その他

- **InferenceSession 生成（ML のみ、プロセス起動後の初回だけ）**: 既定スレッド 35〜52 ms、単一スレッド 31〜38 ms（各実行 3 回 × 2 実行）。上記の合計時間には含まない
- **画像サイズ依存**: ルールの時間は画像全体への bilateralFilter が大半で、画像の画素数に比例する（画素数との相関: 既定 0.90〜0.93、単一 1.00）。
  p95 が中央値より大きいのは約 1 MP の大きい画像のため。ML は 28 点のパッチだけを処理するので画像サイズに依存しない（相関 −0.08〜−0.02）
- **実行順の影響**: 各方式の順位（1〜3 番目）ごとの中央値の差は既定スレッドで 1.4 ms 以内、単一スレッドで 0.2 ms 以内。順位は巡回させているので相殺される
- **再現性（2 回実行）**: 中央値は既定スレッドでルール（本番構成）23.0 / 23.6、ルール（共有）12.5 / 13.0、ML 33.4 / 34.7 ms、
  単一スレッドで 98.5 / 95.6、50.2 / 48.5、149.8 / 146.2 ms。ML / ルール（本番構成）の比は 4 回とも 1.45〜1.53 倍
- **前回計測（ルール 1 条件のみの版）との違い**: 単一スレッドは前回（ルール 49.0 / ML 147.1 ms）とほぼ同じだったが、
  既定スレッドでは今回の方が全体に遅く、特に ML が 28.7 → 34.7 ms になった。実行順・ライブラリ版・スレッド数の設定は同じで、
  ML が最初に実行された場合も遅いことから、並列実行時の PC の状態の違いと考えられる。方式間の比は同じ実行内で比べているので影響を受けにくい

### 考察

- 仮説 2 は支持された。ML は 1 顔あたり中央値 35 ms（既定スレッド）で、本番構成のルールの約 1.5 倍。数十 ms に収まっており、
  静止画の処理としては許容範囲と考えられる
- 前処理を左右で共有した場合と比べると ML は約 2.7 倍になる。本番のルールは同じ画像の前処理を 2 回行っており、
  ML との速度差の半分近くはこの重複に由来する。face_makeup 側で前処理を左右で共有すれば、ルール単体は約 10 ms 速くなる
- ML は推論が支配的（34.7 ms 中 30.3 ms）なので、高速化が必要になった場合は ONNX の量子化やスレッド数の調整が候補になる
- ルールは画像サイズに比例し、ML は依存しないため、高解像度画像では両者の差が縮まる（p95 では本番構成比 1.2 倍）
- **注記: ルールベース版は ROI 切り出しで高速化できる（本実験では未計測）**
  - 本番構成のルールの時間の約 85%（20.4 / 23.6 ms）は画像全体への bilateralFilter だが、エッジ探索が参照するのは
    P から Q 方向へ P-Q 距離の半分まで（P-Q 距離の中央値 9.3 px）の目の周辺だけである
  - 目ごとに ROI（P,Q の外接矩形を探索範囲と bilateralFilter の半径 4 px 分広げたもの）を切り出して前処理すれば、
    前処理は 1 ms 未満、合計は find_edge の約 3 ms 程度になる見込みで、ML との速度差は約 1.5 倍から 10 倍前後に広がると予想される
  - ただし `preprocess` の `cv2.normalize(NORM_MINMAX)` は画像全体の最小・最大で正規化するため、ROI で正規化すると
    微分値の大きさが変わり、絶対値の閾値 `_GRAD_THRESHOLD = 0.1` による検出結果（エッジ位置・fallback）が従来と一致しなくなり得る
  - そのため ROI 版は従来のルールベースとは別の手法として扱い、採用を検討する場合は精度と速度を改めて測る必要がある。
    本実験の受け入れ条件（従来のルールベースとの比較）の結論には影響しない

## 結論

- **受け入れ条件 1（補正点の比較）**: 同じ 4,900 点で比較し、ML 補正がルールベース補正（本番と同じ入力条件）より
  有意に正確であることを確認した（pass_std 42.7% → 90.0%、画像単位 Wilcoxon p = 1.3e-50）
- **受け入れ条件 2（処理時間）**: 同じ 51 顔で計測し、ML 34.7 ms / ルール 23.6 ms（中央値、既定スレッド、本番と同じ左右別 corrector 構成、
  i7-12700、常駐アプリ停止）を記録した。ML はルールの約 1.5 倍で、1 顔あたり数十 ms に収まる。
  前処理を左右で共有したルール（13.0 ms）と比べると約 2.7 倍
